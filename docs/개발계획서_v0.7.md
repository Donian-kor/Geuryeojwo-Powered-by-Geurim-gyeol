0. 방향 변경 사유
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

이전 기획서의 핵심 원칙:

    §3.1 External Runtime Dependency = 0
    ※ ComfyUI, LM Studio, Ollama 등의 외부 실행 프로그램을
      사용하지 않는다.

이 원칙은 유지할 수 없다. 근거는 세 가지다.

  1) 신규 모델 지원 속도
     ComfyUI는 이미지 모델 발표와 같은 주에 그 모델을 지원한다.
     직접 구현하지 않으면 언제나 2~4주 늦고, 그동안 사용자는
     새 모델을 쓸 수 없다. 이는 구조적으로 따라잡을 수 없는
     격차이며, 개인 프로젝트가 이기기에 어려운 게임이다.

  2) 양자화 포맷의 비공개성
     ComfyUI 배포본의 가중치에는 comfy_quant 라 ComfyUI 고유
     패킹 형식이 사용된다. 실제 측정 결과:
       - Qwen-Image 2.1 : 841개 텐서 중 192개(22%)가 NVFP4 패킹
       - Qwen3VL 텍스트 인코더 : 1258개 중 254개(20%)가 int8 패킹
     이 형식을 해석하는 코드는 ComfyUI 내부에만 존재한다.

  3) 실제로 수행한 검증
     - QwenImageTransformer2DModel.from_single_file → 실패
       (config.json 을 HuggingFace 에서 받으려 시도)
     - AutoencoderKLQwenImage.from_single_file → 실패
       (FromOriginalModelMixin 미지원.
        diffusers 0.40.0 에 해당 클래스 자체가 없음)
     - AutoPipelineForText2Image.from_pretrained → HFValidationError
     즉 폴더 구조를 어떻게 구성하든 가중치 자체를 읽을 수 없다.

결론: "외부 의존성 0"과 "사용자가 가진 모델로 이미지를 생성한다"는
동시에 달성할 수 없다. 후자를 우선한다.

이 프로그램의 목적은 모델 지원 범위가 아니라 다음이다.

    "AI 이미지 생성의 복잡성을 사용자에게 보여주지 않는다."

ComfyUI가 모델 실행을 담당하고, 이 프로그램이 사용자의 접점
(프롬프트 입력, 모델 선택, 결과 확인, 기록)을 담당한다.

3. 역할 분담
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

이 프로그램이 하는 일:
    - 사용자 입력(프롬프트, 모델, 파라미터) 받기
    - 워크플로 JSON 생성 후 ComfyUI에 제출
    - 진행률 / 완료 / 오류를 실시간 수신
    - 결과 이미지를 세션 기록과 출력 폴더로 정리
    - 서버 상태와 VRAM 정보를 사용자에게 설명

이 프로그램이 하지 않는 일(ComfyUI 담당):
    - 모델 파일 읽기 및 가중치 해석
    - U-Net / Transformer / VAE 실행
    - 양자화 및 비양자화 변환
    - VRAM 스와핑 및 오프로딩
    - 프롬프트 확장(인핸서 LLM 호출)

사용자에게 VRAM 상태를 보여주는 기능은 ComfyUI의 /system_stats 조회로
구현한다. 그 조회 결과는 주기적으로 갱신되지 않고,
[상태 새로고침] 또는 워크플로 변경 시점의 값으로 표시된다(§10.5).

프롬프트 확장은 이 프로그램의 app/prompt/ 가 아니라 워크플로 안의
노드(예: QwenImage21PromptEnhancerT8)가 담당한다. GUI에는
"프롬프트 인핸서 사용" 스위치 하나만 있고, 끄면 그 노드를 그래프에서
빼고 사용자 프롬프트를 인코더에 직접 넣는다(§10.3-B3).

4.1 ComfyUI 실행 조건

    ComfyUI가 --api 플래그로 실행 중이어야 한다.

        python main.py --api --port 8188

    이 프로그램은 기본적으로 ComfyUI를 자동으로 실행하지 않는다.
    사용자가 직접 실행하며, 이미 실행 중이면 감지해 재사용한다.
    config/comfyui.json 의 auto_launch 를 true 로 켜면
    이 프로그램이 띄우는 쪽으로 전환된다(§4.4).

    설정 파일 config/comfyui.json:
        {
          "host": "127.0.0.1",
          "port": 8188,
          "timeout_seconds": 300,
          "connect_timeout_seconds": 5,
          "auto_launch": false,
          "launch_command": "",
          "launch_working_dir": "",
          "launch_wait_seconds": 90,
          "model_folders": [
            "checkpoints", "diffusion_models", "vae",
            "loras", "text_encoders"
          ]
        }

    ※ host/port 이라는 키 이름을 쓴다. base_url 키는 읽지 않는다
      (README 에 남아 있는 구 키 — §10.4-B9).

4.2 사용하는 API

| 메서드 | 경로 | 용도 | 코드 위치 |
|---|---|---|---|
| GET  | /system_stats | VRAM / 장치 정보 표시 | get_system_info |
| GET  | /object_info/{node} | sampler·scheduler 선택지 | get_object_info |
| GET  | /models | 모델 폴더 목록 | get_model_folders |
| GET  | /models/{folder} | 폴더별 모델 목록 | get_models |
| GET  | /queue | 실행 대기열 상태 | get_queue |
| POST | /prompt | 워크플로 제출 | queue_prompt |
| WS   | /ws?clientId= | 진행률 실시간 수신 | run |
| GET  | /history/{prompt_id} | 실행 결과 조회 | get_history |
| GET  | /view | 결과 이미지 다운로드 | get_image |
| POST | /interrupt | 실행 중단 | interrupt |
| POST | /free | 모델 언로드(메모리 정리) | post_free |

    경로 형식에 주의: /models 에 folder 를 질의로 붙이는
    (?folder=checkpoints) 방식이 아니라 경로로 붙인다.
    get_all_models() 는 config.model_folders 의 각 폴더를
    순차 호출해 하나의 dict 로 합친다.

4.3 POST /prompt 요청 형식

    요청:
    {
      "prompt": {
        "3": {
          "class_type": "KSampler",
          "inputs": {
            "seed": 123456,
            "steps": 30,
            "cfg": 7.0,
            "sampler_name": "euler",
            "scheduler": "normal",
            "denoise": 1.0,
            "model": ["4", 0],
            "positive": ["6", 0],
            "negative": ["7", 0],
            "latent_image": ["5", 0]
          },
          "_meta": {"title": "KSampler"}
        }
      },
      "client_id": "<uuid>"
    }

    응답:
    {
      "prompt_id": "uuid",
      "number": 1,
      "node_errors": {}
    }

    링크 표현: ["출발 노드 id", 출력 슬롯 번호]
    예) ["4", 0] 은 4번 노드의 0번 출력

    queue_prompt() 는 node_errors 가 비어 있지 않을 때
    예외를 던져 사용자에게 "노드를 찾을 수 없습니다" 류의
    메시지를 그대로 전달한다.

4.4 WebSocket 메시지

| type | data 주요 필드 | run() 의 처리 |
|---|---|---|
| status | status, queue | 무시 |
| execution_start | prompt_id | 단계 표시 |
| executing | node, prompt_id | node 가 null 이면 완료로 간주 |
| progress | value, max, node, prompt_id | 10~90% 로 매핑 |
| executed | node | 단계 표시 |
| execution_error | exception_message | 오류로 종료 |
| execution_interrupted | - | 중지로 종료 |

    progress 의 value / max 로 진행률 매핑을 수행한다.

    ※ prompt_id 로 메시지를 걸러내지 않는다(§10.3-B2).

자동 실행(auto_launch) 규칙:
    - launch_command 에 --api 와 --port 가 없으면 자동으로 붙인다.
      이미 있으면 중복해서 붙이지 않는다.
    - 경로에 공백이 있으면 그 부분만 따옴표로 감싸게 된다.
    - 이 프로그램이 띄운 프로세스만 종료한다(stop_launched).
      사용자가 직접 실행한 ComfyUI 는 건드리지 않는다.
    - 종료 시 POST /free 로 모델을 먼저 내린 뒤 terminate 하고,
      그래도 안 죽으면 kill 한다.
    - 현재 구현은 이 대기를 호출한 스레드를 그대로 블로킹한다
      (§10.3-B1).

5.1 워크플로 정의

    ComfyUI API 형식 JSON 으로 저장한다.

    workflows/
    ├── qwen-image-2.1.json
    └── ...

    각 파일의 최상위 구조:
    {
      "name": "기본 txt2img",
      "description": "표준 텍스트→이미지 생성",
      "output_node": "8",
      "prompt": { ...API 형식 워크플로... },
      "parameters": {
        "model":     {"node": "4",  "input": "unet_name"},
        "steps":     {"node": "3",  "input": "steps"},
        "cfg":       {"node": "3",  "input": "cfg"},
        "seed":      {"node": "3",  "input": "seed"},
        "sampler":   {"node": "3",  "input": "sampler_name"},
        "scheduler": {"node": "3",  "input": "scheduler"},
        "width":     {"node": "5",  "input": "width"},
        "height":    {"node": "5",  "input": "height"},
        "positive":  {"node": "6",  "input": "text"},
        "negative":  {"node": "7",  "input": "text"},
        "vae":       {"node": "8",  "input": "vae_name"},
        "lora":      {"node": "10", "input": "lora_name"}
      }
    }

    prompt 키가 없는 파일은 문서 전체를 워크플로로 본다.
    (ComfyUI 화면의 Export (API) 결과를 그대로 넣어도 읽힌다)

    parameters 맵 덕분에 GUI 위젯과 워크플로 노드가 코드 수정 없이
    연결된다. 새 워크플로를 추가해도 GUI 코드는 바뀌지 않는다.

    주의:
    - parameters 맵의 key 이름은 자유다. 값 주입과 메타데이터
      기록은 spec.input (ComfyUI 입력 이름)으로 조회한다.
      (예: key "sampler" + input "sampler_name" 조합이 정상)
    - links(배열)로 연결된 입력은 덮어쓰지 않는다.
      사용자가 넣은 값이 조용히 버려진다(§10.5).

5.2 parameters 맵이 없을 때 (자동 추론)

    load_workflow() 는 parameters 가 비어 있으면
    infer_parameters() 로 채운다. 추론 규칙:

      positive  : 값이 링크가 아닌 문자열인 prompt/text/positive
                  입력 중, KSampler 쪽으로 가는 경로가 가장 짧은 것
      negative  : negative_prompt 입력
      seed/steps/cfg/denoise/sampler_name/scheduler :
                  SaveImage 쪽으로 흘러가는 실제 샘플러 노드의 것만
      unet/checkpoint/clip/vae/lora :
                  unet_name, ckpt_name, clip_name, vae_name, lora_name
                  입력 (kind = "model:<폴더>")
      그 외      : seed/steps/width/height/batch_size/cfg/denoise/
                  guidance/resolution/max_output_chars/
                  strength_model/strength_clip/sampler_name/scheduler

    이 규칙은 Qwen-Image 2.1 워크플로(인핸서 노드 + LoRA +
    Qwen3VL 인코더)에서 검증했다. 인핸서 노드는 class_type 에
    TextEncode 가 없지만 프롬프트를 실제로 받으므로 positive 로
    잡히고, 인핸서의 seed 와 KSampler 의 seed 가 공존할 때는
    KSampler 쪽만 선택된다.

5.3 워크플로 선택

    - 시작 시 /models 와 /object_info 를 조회해 사용 가능한
      sampler·scheduler·모델 목록을 얻는다.
    - workflows/ 폴더를 스캔해 선택 목록을 GUI에 제공한다.
    - 활성 워크플로는 config/workflow.json 이 아니라
      메모리에만 있다. 프로그램 재시작 시 파일명 순 첫 번째로
      되돌아간다(§5.3).

5.4 모델 선택

    ComfyUI의 모델은 폴더 기반이다. 이 프로그램은 ComfyUI의
    모델 폴더를 직접 읽지 않고 /models/{folder} API로 이름을 받는다.

        GET /models/diffusion_models
        GET /models/vae
        GET /models/loras

    이 방식 덕분에 ComfyUI의 extra_model_paths.yaml 설정,
    심볼릭 링크, 여러 모델 경로가 그대로 반영된다.

    GUI는 워크플로에 해당 입력이 있을 때만 드롭다운을 활성화하고,
    ComfyUI 응답이 없으면 워크플로 기본값 하나만 표시한다.

           (모델 캐시 적중, 간단한 워크플로) `executing` +
           node=null 메시지가 WebSocket 연결 전에 이미 지나간다.
           그러면 루프는 timeout_seconds(기본 300초)까지
           "생성 중" 으로 멈췄다가 "실행 시간이 초과되었습니다" 로
           끝난다. 실제로는 이미 끝난 작업이다.
    추가 : prompt_id 로 메시지를 걸러내지 않는다
           (run 안에 prompt_id 비교가 없다). 같은 ComfyUI 를
           다른 프로그램이 쓰는 중이면 남의 완료 신호로
           여기서도 완료로 판정할 수 있다.
    조치 : WebSocket 을 먼저 열고 client_id 로 구독한 뒤
           POST /prompt 하도록 순서를 뒤집고,
           모든 메시지에서 data.prompt_id 가 Ours 와 같은지 확인.

B3. 인핸서 우회가 LLM 호출을 막지 않는다
    위치 : engine._bypass_enhancer(366)
    문제 : node 4(TextEncode) 의 prompt 연결만 끊는다.
           그런데 node 15(T8ShowText) 가 여전히 node 14 를
           ["14", 0] 으로 참조한다. ComfyUI 는 출력 노드로
           도달 가능한 노드를 실행하므로, 우회 후에도 그래프에
           인핸서가 남아 있으면 LLM 이 호출된다.
           확인 : 우회 후 payload 에서 '14' 를 참조하는 노드는
           ['15'] 로 남는다.
    추가 : "불필요한 LLM 호출을 막기 위해 우회 사실을 기록한다" 는
           주석과 달리 기록만 하고 아무도 읽지 않는다.
           wf.meta 는 워크플로가 로드된 뒤 계속 재사용되는
           객체이므로, 생성할 때마다 '14' 가 쌓인다
           (3회 실행 → ['14','14','14'] 확인).
    조치 : 우회 시 참조 노드를 함께 끊거나, 인핸서 노드를
           payload 에서 제거한다. 기록은 로그로만 남긴다.

B4. 메타데이터에 "실제로 쓰인 프롬프트" 가 없다
    위치 : engine._applied_values(468)
    문제 : 인핸서를 켜면 node 14 의 prompt 입력에는 사용자가
           쓴 원문이 들어 있고, 실제 이미지 생성에 쓰인 것은
           인핸서가 다듬은 출력이다. 그런데 기록되는 값은
           node 14 의 입력값, 즉 원문이다.
           확인 : enhance ON + prompt "고양이 한 마리"
           → metadata prompt = '고양이 한 마리' (원문 그대로)
    영향 : 세션/출력 JSON의 prompt 로는 같은 그림을 다시 만들 수
           없다. §12 성공 기준 "시드 재현성" 이 이 워크플로에서
           성립하지 않는다.
    조치 : ComfyUI history 의 인핸서 노드 출력을 읽어
           실제 사용 프롬프트를 함께 기록한다.

B5. 파일 덮어쓰기 (데이터 손실)
    위치 : output/manager.save_output(103) — index = len(existing)+1
           session/manager.create_session(97) — 같은 방식
    문제 : 인덱스를 "현재 파일 개수 + 1" 로 매기면, 중간 파일이
           지워졌을 때 이미 있는 파일과 겹친다.
           확인 1 (outputs): 3개 저장 → 첫 번째 삭제 → 같은
           seed 로 저장 → 기존 img_002_seed9.png 가 조용히
           덮어써졌다.
           확인 2 (sessions): 001/002 생성 → 001 삭제 → 새로
           생성 → 살아 있던 002 세션 폴더를 그대로 재사용하고
           session.json 을 덮어썼다.
    조치 : 최대 번호를 읽어 +1 하거나(최대값 방식),
           UUID/타임스탬프 기반 이름을 쓴다.

B6. VRAM 표시가 예외를 던진다
    위치 : client.SystemInfo.describe() 와
           main_window._update_status_bar(341)
    문제 : vram_total_gb 은 있고 vram_free_gb 이 None 인
           상태에서 {self.vram_used_gb:.1f} 로 포맷하면
           TypeError: unsupported format string passed to
           NoneType.__format__ 가 난다 (확인).
           GPU 없는 환경이나 /system_stats 응답이 불완전한
           경우에 해당한다. 상태창은 1초마다 호출된다.
    조치 : 포맷 전에 None 여부를 함께 확인한다.

10.4 🟠 고치는 편이 좋은 것

B7. 실행이 끝난 뒤에도 UI 가 3~5초 더 멈춘다
    client.close() 는 현재 이벤트 루프에 묶인 클라이언트만
    닫는다. 엔진은 asyncio.run 을 반복 호출하므로 루프가 매번
    바뀌고, 그때마다 새 httpx.AsyncClient 가 만들어진다
    (5회 호출 → 클라이언트 5개 생성, 닫힌 것 0개, 확인).
    이전 클라이언트는 aclose() 되지 않은 채 GC 에 맡겨지고,
    워크플로 한 장을 저장할 때도 이미지마다 asyncio.run 이 새로
    도는 만큼 같은 일이 반복된다.
    조치 : 엔진 소유 루프를 하나로 통일하거나,
           클라이언트를 생성한 루프에서 close 하도록 한다.

B8. pytest 가 실제로 못 잡는 것들
    - client.run() 의 WebSocket 대기 루프: 전부 monkeypatch 처리
      되므로 §10.3-B2 를 놓친다. 로컬 WebSocket 서버를 띄우는
      통합 테스트가 필요하다.
    - B5 두 건(파일 덮어쓰기): 출력/세션 저장 테스트가 있으나
      "중간 삭제 후 재저장" 시나리오가 없다.
    - B3 인핸서 우회, B4 메타데이터 프롬프트: 테스트 없음.
    - GUI 전체: 테스트 0개.

B9. 잡음 — 지우거나 정리할 것

10.5 설계상 감수할 부분 (버그 아님)

      ComfyUI 라는 선택의 대가이며, 문서화해 두는 것으로
      충분하다.

이 문서의 규정은 다음과 같다.

    "ComfyUI 는 그림결의 필수 구성요소다"

그림결과 ComfyUI 는 하나의 프로세스 쌍으로 동작한다.
그림결은 ComfyUI 를 직접 호출하고,
ComfyUI 는 그림결에 실행 결과를 반환한다.
둘은 분리된 프로세스이며 HTTP 로 통신한다.

    그림결이 제공하지 않는 것:
        모델 실행, 가중치 해석, 양자화, 메모리 관리,
        프롬프트 확장

    그림결이 제공하는 것:
        입력 경험, 파라미터 매핑, 결과 기록, 사용자와의 접점

이것은 "그려줘 가 ComfyUI 다"가 아니라
"그려줘 는 ComfyUI 를 다루는 도구다"이다.
사용자에게는 하나의 프로그램으로 보이며,
안에서는 역할이 나뉜다.

사용자가 감당하지 않아도 되는 것은 세 가지다:
    1. ComfyUI 설치와 GPU 환경 구성
    2. 가중치 포맷과 양자화
    3. 새 모델이 나왔을 때의 대응

사용자가 대신 감당하는 것은 세 가지다:
    1. 워크플로 JSON 을 workflows/ 에 넣는 일
    2. 모델 파일을 ComfyUI 모델 폴더에 두는 일
    3. 자신의 프롬프트를 고치는 일

# v0.7 구조 개선 및 안정화 업데이트

## 1. 버전 목적

v0.7은 v0.6 기준본의 기능 방향을 유지하면서 다음 두 축을 동시에 완성하는 버전이다.

1. **그림결(Grim-gyeol) 엔진의 ComfyUI 실행 안정성 강화**
2. **GUI 전체를 기능 단위로 모듈화하여 폴더 구조만 보아도 책임 범위를 이해할 수 있도록 개선**

v0.7에서도 이미지 생성 자체는 ComfyUI가 담당한다. 그림결은 ComfyUI의 API/Workflow를 안전하게 제어하고, 그려줘 GUI는 사용자가 ComfyUI의 복잡성을 직접 다루지 않도록 추상화한다.

## 2. v0.7 핵심 원칙

### 2.1 Engine / GUI 완전 분리

GUI는 ComfyUI API를 직접 호출하지 않는다.

```text
GUI
 ↓
GUI Controller
 ↓
Worker
 ↓
그림결 Engine
 ↓
ComfyClient / WebSocket
 ↓
ComfyUI
```

Engine은 GUI 프레임워크에 의존하지 않는다.

### 2.2 ComfyUI 통신 단일화

모든 HTTP/WebSocket 통신은 `app/engine/comfy/` 아래에서만 수행한다.

```text
app/engine/comfy/
├── client.py
├── websocket.py
├── compatibility.py
└── process.py
```

ComfyUI API 변경 시 GUI와 Workflow 코드를 수정하지 않고 이 계층에서 대응한다.

### 2.3 생성 단위와 결과 단위 분리

하나의 ComfyUI 실행이 여러 이미지를 반환할 수 있으므로 `Generation`과 `Image Result`를 분리한다.

```text
Generation
├── generation_id
├── prompt
├── enhanced_prompt
├── workflow
├── seed
└── results
    ├── image 1
    ├── image 2
    └── image 3
```

### 2.4 재현성 우선

생성 기록에는 사용자가 입력한 원본 프롬프트와 실제 이미지 모델에 전달된 최종 프롬프트를 구분해서 저장한다.

```json
{
  "original_prompt": "...",
  "enhanced_prompt": "...",
  "negative_prompt": "...",
  "workflow": "...",
  "workflow_hash": "...",
  "model": "...",
  "seed": 1234
}
```

### 3.1 MainWindow 책임

`main_window.py`는 화면 조립과 페이지 전환만 담당한다.

ComfyUI API 호출, 파일 저장, Workflow 수정, 생성 로직을 직접 구현하지 않는다.

### 3.2 Pages 책임

`pages/`는 실제 화면 기능 단위다.

- `generation/`: 이미지 생성
- `gallery/`: 결과 이미지 탐색
- `sessions/`: 세션 관리
- `settings/`: 프로그램 설정

### 3.3 Widgets 책임

`widgets/`는 여러 화면에서 재사용 가능한 UI 부품만 둔다.

### 3.4 Controllers 책임

Controller는 UI 이벤트를 Engine 작업으로 변환한다.

GUI 위젯이 Engine 객체를 직접 제어하지 않는다.

### 3.5 Workers 책임

네트워크, ComfyUI 통신, 장시간 작업은 GUI 스레드에서 실행하지 않는다.

## 4. v0.7 필수 안정화 항목

### B1. GUI Blocking 제거

모든 ComfyUI 네트워크 호출과 장시간 작업을 Worker로 이동한다.

`QApplication.processEvents()`를 blocking 회피 수단으로 사용하지 않는다.

### B2. WebSocket 실행 순서 수정

반드시 다음 순서를 사용한다.

```text
WebSocket 연결
 ↓
client_id 준비
 ↓
POST /prompt
 ↓
prompt_id 확보
 ↓
WebSocket 이벤트 수신
 ↓
내 prompt_id와 일치하는 이벤트만 처리
```

생성 완료 이벤트를 놓치지 않도록 WebSocket을 먼저 준비한다.

### B3. Prompt Enhancer OFF 완전 우회

Enhancer를 OFF하면 해당 노드뿐 아니라 연결된 출력/표시 노드까지 실행 경로에서 제거하거나 안전하게 우회한다.

실행이 필요 없는 Enhancer 노드가 남아 있지 않아야 한다.

### B4. 실제 Enhanced Prompt 저장

원본 사용자 입력과 실제 이미지 생성에 사용된 최종 프롬프트를 별도로 저장한다.

### B5. 파일/세션 ID 충돌 방지

파일 개수 기반 번호 계산을 사용하지 않는다.

생성 ID와 세션 ID는 충돌 방지 가능한 고유 식별자를 사용한다.

### B6. VRAM 정보 누락 방어

`vram_free` 등의 값이 없는 경우에도 GUI가 예외로 종료되지 않는다.

### B7. asyncio 수명 관리

반복적인 `asyncio.run()` 호출을 제거하고 ComfyUI 통신용 Worker/Event Loop의 수명을 명확히 관리한다.

### B8. Prompt-specific Interrupt

가능한 경우 현재 생성의 `prompt_id`를 사용하여 해당 작업만 취소한다.

### B9. 설정과 실제 동작 일치

모델 폴더 목록, ComfyUI 주소, timeout 등의 설정값을 코드에 하드코딩하지 않는다.

## 5. Workflow / Prompt 규칙

Workflow의 명시적 parameter mapping을 자동 추론보다 우선한다.

```text
1. 명시적 parameter mapping
2. Workflow 자동 추론
3. 지원하지 않는 파라미터는 명확한 오류/경고
```

Prompt Enhancer는 ComfyUI 자체 기능으로 간주하지 않고, **선택된 Workflow에 포함된 Prompt Enhancer Node의 기능**으로 정의한다.

## 6. 저장 구조

권장 결과 구조:

```text
outputs/
└── 2026-10-01/
    └── 173522_8f31/
        ├── 001.png
        ├── 002.png
        ├── 003.png
```

`generation.json`에는 해당 실행의 Workflow, prompt, seed, 모델, 결과 파일 목록 및 재현에 필요한 정보를 저장한다.

## 9. v0.7 완료 기준

- GUI 네트워크 작업이 메인 스레드를 block하지 않는다.
- WebSocket 이벤트를 놓치지 않는다.
- 다른 prompt의 이벤트를 자신의 작업으로 오인하지 않는다.
- Prompt Enhancer OFF가 실제 실행 경로에서 완전히 우회된다.
- 원본/최종 Prompt가 구분되어 저장된다.
- 결과 파일과 세션 ID가 충돌하지 않는다.
- VRAM 정보가 누락되어도 UI가 정상 동작한다.
- ComfyUI 통신이 `app/engine/comfy/` 계층으로 집중된다.
- GUI 기능이 `pages / widgets / controllers / workers`로 구분된다.
- MainWindow가 생성/저장/ComfyUI 통신의 세부 구현을 직접 담당하지 않는다.
- 기존 테스트가 유지되고 새 안정화 테스트가 추가된다.

## 10. v0.7 이후 방향

v0.7의 목표는 새로운 이미지 모델을 직접 구현하는 것이 아니다.

ComfyUI의 발전을 따라갈 수 있도록 그림결의 경계를 안정화하고, 그려줘가 ComfyUI의 복잡한 Workflow와 모델 구성을 사용자에게 단순한 생성 경험으로 제공하는 것을 우선한다.

새로운 이미지 모델 지원은 가능하면 다음 방식으로 추가한다.

```text
새 모델
 ↓
ComfyUI Workflow
 ↓
Workflow Profile
 ↓
그림결 parameter mapping
 ↓
그려줘 GUI
```

이를 통해 모델이 변경될 때 GUI와 Engine 전체를 다시 작성하지 않는다.
